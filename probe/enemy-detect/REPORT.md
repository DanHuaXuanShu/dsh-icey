# 画面内敌人检测 · 标定报告（probe/enemy-detect）

> 写于 2026-10-26。作者：enemy-detect（子代理）。
> 结论先放这里：**这条路在现有帧上做不到可用精度。不建议进 `lib/`。**
> 下面的数字都是真跑出来的；每一条「看起来能用」的判据后面都标了它实际错在哪。

---

## 0. 一句话

能稳定拿到的只有「玩家大概在画面哪一侧」，而**敌人和玩家的位置都被各自的大招特效盖住**，
单帧像素统计分不开「敌人」「特效」「霓虹灯牌」「金色强化台」这四样东西。
检测器在 `shots/combat` 上只有 **39.8%** 的帧给出方向，抽检这 39.8% 里的 10 张，**3 张方向错**；
在 `shots/watch`（探索）上有 **11.2%** 的帧误报。

## 2. 试过、量过的特征（含失败原因）

### 2.1 「跟背景反差大的大块」= 局部对比度物体（失败）
做法：亮度减 5×5 邻域均值当「物体响应」，阈值 + 连通域。
结果：命中的全是**地面反光、窗格、墙面管道、玩家自己的光**；坦克机器人反而因为身上大面积暗色装甲而响应不强。
一帧里通常有 3~6 个候选块，和敌人对不上。放弃。

### 2.2 暖色发光团（部分有效，但被三样东西吃掉）
暖色判据（最终版）：
```
lum >= 62 且 r - b >= 28 且 r >= 72 且 b <= 150 且 g - b <= 120
```
实测各暖色源在「动作带 y∈[0.18,0.93]」里的**逐列密度**（按 120 列网格统计，480 宽分析帧）：

| 来源 | 位置 | 列密度 | 纵向跨度 |
|---|---|---|---|
| **画面下沿黄色能量槽** | x≈0.40–0.60, y≈0.87 | **14.8%（每一帧都有，连纯黑过场帧 c0021/c0085 都有）** | 0.01 |
| 左下连击数（黄字） | x≈0.09–0.16, y≈0.25–0.31 | 10~93% | 0.06 |
| 强化台（负样本里的金色台子） | x≈0.69, y≈0.54–0.63 | **76~78%** | 0.09 |
| 墙上霓虹灯牌 | x≈0.06–0.12, y≈0.42–0.60 | 5~9% | 0.18 |
| 坦克机器人的发光眼/金饰 | 敌人所在列 | 3~8%（480 宽）／7~11%（原生 640 宽） | 0.10–0.14 |
| 背景墙/路面 | 其他列 | 0~1% | — |

结论：**敌人自己的暖像素是稀疏的小亮点**（全画面最大的暖色连通块只有画面的 0.03%~0.6%），
构不成「大块暖色物体」；而 HUD、能量槽、强化台、霓虹反而更「整」。这是这个方向最根本的障碍：
**在像素统计上，强化台比敌人更像「敌人」。**

### 2.3 玩家的青色定位（不稳）
青色判据（比 `probe/track-hero.mjs` 收紧一档）：
```
lum > 130 且 b > 175 且 g > 150 且 r < 155 且 b - r > 65 且 b - g < 60
```
- 竞技场两端有**青色战斗屏障**（竖直，x 贴边，跨 y 0.35~0.47），贴边一律不看才能排掉。
- 她的**剑光/大招也是青色**：`c0037` 里 x≈0.61 那一列青色占比超过 100%（补满整列），
  裁剪 5x 放大确认那里**只有一大团蓝白爆炸，没有人**。
- 玩家本人在 0.10×0.35 的框里也只有 10~30% 的像素是青光（p50 亮度 34、p90 亮度 243），
  缩到 480 宽以后更稀。
结果：593 张战斗帧里 **17.4% 根本找不到玩家**；找到的那些也常在「特效中心」而不是「脚下」。

### 2.4 相邻帧运动差分（不可用）
`c0140→c0141` 变化像素 **27.1%**，`c0160→c0161` **30.0%**，`c0520→c0521` **44.8%**。
虽然 `combat3 f_000→f_001` 只有 0.93%、`watch` 只有 5.16%，
说明战斗帧之间相隔太长（约 2.5 秒/帧，593 张覆盖 1474 秒），背景早就换过了。
**这批磁盘帧不是连拍**，动不了「运动区域」这条思路；要用运动只能在实时循环里另做（见 §5）。

### 2.5 最终版检测器的判据（`detect.mjs`）
1. 排除区（归一化）：标题栏+HUD 上沿、左下血/盾/连击、右上金钱、**下沿黄色能量槽**、底部字幕条；
   左右各 5% 贴边不看。
2. 玩家：青色连通块里挑「高 5%~55%、宽 ≤24%、块大、贴地」的一块，落点取块体下半部质心。
   找不到玩家 → 直接返回 `null`（宁缺勿错）。全屏青色占比 >9% → 也返回 `null`（大招糊屏）。
3. 敌人：动作带里逐列暖色密度 → 3 列平滑 → 阈值 **0.030** 合并成「带」，
   要求带宽 ≥ **3%**、带内暖色纵向跨度 ≥ **0.06**；离玩家 < **4.5%** 的带（自己的剑光/身体）丢掉。
4. 取分最高的带，`side = 带中心 < 玩家 x ? 'left' : 'right'`；`conf` 由密度/宽度/高度加权。

## 3. 两组数字（480 宽，等于插件默认 `analysisWidth`）

### 3.1 正样本：`shots/combat`（593 张，640x373 → 缩到 480x280）

| 指标 | 数值 |
|---|---|
| 给出方向（`side != null`） | **236 / 593 = 39.8%** |
| 不给出方向（**无法判定**） | 357 / 593 = 60.2%（其中 103 张是「找不到玩家」= 17.4%） |
| 给左 / 给右 | 132 / 104 |
| 置信度中位 | 0.83（最低 0.39） |

**注意：这批帧没有标注，所以 39.8% 不是「准确率」，只是「覆盖率」。**
为了知道覆盖率里的对错，我按「抽到的帧逐张目视」做了两次人工核对：

- **A 组（每 16 帧取 1，共 12 张：c0005…c0181）**：10 张有敌人、2 张是纯黑过场。
  检测器 **10 张全部返回 null**（这一段的覆盖率只有 10.0%，刚好没抽中）→ 无法判定，按 0 计。
- **B 组（c0405…c0590 每 15 帧取 1，共 13 张）**：7 张给出了方向。
  逐张看标记图（绿圈=检测到的敌人、蓝圈=检测到的玩家）：
  **方向对 5 张**（c0435 c0450 c0495 c0510 c0575）、**方向错 2 张**（c0465、c0555）。
  错的这两张，检测器咬住的是**左侧墙上的红色霓虹灯牌**，而敌人其实在右边。
- 另一小组 3 张（c0310 c0460 c0510）：对 2 错 1（c0460 咬的是霓虹灯牌）。

把两次合起来：**在「给出方向」的帧里，目视复核 10 张，方向对 7 张、错 3 张（≈70%）**。
样本只有 10，置信区间很宽（大约 40%~90%），只能当「明显不到可用」的证据，不能当准确率。

### 3.2 负样本（不该给方向）

| 集合 | 规模 | 给出方向（误报） | 说明 |
|---|---|---|---|
| `shots/combat3`（强化台旁空地） | 40 | **0（0.0%）** | ⚠️ 但这个 0 是「找不到玩家」导致的 bail-out（32/40 帧没定位到玩家），**不是**识别出「那是强化台」。判据本身并不排除强化台（§2.2 里它是最强的暖色源）。 |
| `shots/combat2` 的 f_*.png | 40 | **0（0.0%）** | 同上（40/40 帧没定位到玩家） |
| `shots/watch`（探索 500 张） | 500 | **56（11.2%）** | 抽 2 张看着火点：`w0380` 咬的是**路边棕色树影/土路**（明确误报）；`w0340` 咬的是画面里一个小机器人（探索区确实有怪，不算纯误报）。 |

**把这两行放在一起看才是重点**：两个 1280x745 的负样本「零误报」，靠的是「玩家定位失败 →
提前返回 null」这条兜底，不是因为判据学会了区分空地和敌人。换个视角看就是：
**判据在该给答案的时候经常不给，而在给了答案的地方约有 1/3 是错的。**

### 3.3 覆盖率的分布（说明它不是均匀失效）

| 帧段 | 给出方向 |
|---|---|
| c0001–c0200 | 10.0% |
| c0201–c0400 | 48.5% |
| c0401–c0593 | 61.7% |

前 200 帧（大量过场/大招/纯黑帧）几乎全放弃；后段覆盖率能到六成，但目视复核看到的后段错误
（霓虹灯牌）也集中在后段 —— 场景越像「暗巷 + 红招牌」，越容易错。

### 3.4 开销

含 PNG 解码 + 缩放的离线批量：480 宽 ≈ **28.5 ms/帧**（593 张），1280 宽的两组 ≈ **69 ms/帧**。
检测函数本身只做两遍 O(W×H) 扫描，实时用的话建议在 `analysisWidth=480` 上跑，
但**这个信息价值不值得付这个开销**（见 §4）。

## 4. 什么情况下会失效（实测到的，不是猜的）

1. **自己的大招/剑光糊屏**（`c0020 c0037 c0069`）：青色/白色爆炸盖住玩家和敌人。这是最常见的失效。
2. **暗巷 + 红霓虹灯牌**（`c0460 c0465 c0555`）：灯牌就是「一大条高密度暖色」，与敌人完全同构，
   检测器有 3/10 的抽样次咬到了它。
3. **纯深色的怪**（`c0320` 蜘蛛雷，黑球+红核）：几乎没有暖像素，漏检。
4. **金色强化台**（`combat3`/`combat2` 的 76~78% 暖色带）：判据无法把它和「金色机器人」区分。
   这次没误报只是因为它出现的场景里玩家没被定位到。
5. **玩家贴边 / 半出画**：贴边 5% 一律不看，玩家在边上时 `side` 失去参考点。
6. **过场/黑屏帧**（`c0021 c0085`）：有 HUD 但没画面，任何判据都不该给答案（目前靠 bail-out 兜住）。
7. **探索场景的暖色地形**（`w0380` 树影/土路）：11.2% 的探索帧误报主要来自这里。

## 5. 为什么建议不要进 `lib/`（我的判断）

- 决策层要的是「往哪边走」。给错的代价 > 不给：敌人在身后时朝反方向走 = 送背身，
  而不给方向至少还能退回现在的 `chase`（U 键，游戏自带索敌）。
- 现有实现：60% 的帧没有答案，给了答案的约 1/3 是错的，探索时 11%/帧 误报。
  autoplay 的循环是 200~500 ms 一次，误报会直接把「移动方向」带偏。
- 三个负样本集合的「0 误报」不可信（靠玩家定位失败兜底），别拿这个当通过标准。

**如果要继续做，我建议的方向（按性价比）**：
1. **先拿实时帧做两帧差分**：这套磁盘帧相隔 2.5 秒没法用，但实时循环里 `analyzeFrame` 本来就有上一帧
   （`prev`）。在 100~200 ms 间隔上，背景基本不动，玩家+敌人是主要变化区，
   再按「青色 = 玩家」扣掉自己 → 剩下的变化区就是敌人/弹幕。这是唯一一个「不依赖外观」且我这里无法离线验证的方向。
2. **标 200~400 帧、训一个 32x32 输入的小 CNN（或逻辑回归）**：`shots/combat` 有 593 张，
   标 side 的活干完就能训；输入缩到 64x36 灰度+色度，模型小到可以纯 JS 手写前向。
   这是真正能解决「金色强化台 vs 金色机器人」这类语义区分的路。
3. **别用像素方向，改用「打得到打不到」的反馈**：连击数在掉 = 这一刀打中了；
   连击数长时间不涨 + 命中特效不在前方 = 转身。用游戏给的反馈做闭环，比单帧识别稳。

## 7. 复核方法（想自己验一遍）

```powershell
node --check probe/enemy-detect/detect.mjs
node --input-type=module -e "import {decodePng} from './lib/png-decode.mjs'; import {resizeRgba} from './lib/png.mjs'; import {detectEnemies} from './probe/enemy-detect/detect.mjs'; import fs from 'node:fs'; let hit=0,n=0; for (const f of fs.readdirSync('shots/combat').filter(x=>/^c\d+\.png/.test(x))) { const img=decodePng(fs.readFileSync('shots/combat/'+f)); const h=Math.max(1,Math.round(img.height*480/img.width)); const r=detectEnemies({rgba:resizeRgba(img.rgba,img.width,img.height,480,h),width:480,height:h}); n++; if(r.side)hit++; } console.log(hit+'/'+n, (hit/n*100).toFixed(1)+'%');"
```

第二条命令我在本机跑过，输出 `236/593 39.8%`，和 §3.1 一致。（负样本把 `shots/combat` 换成
`shots/combat3` / `shots/combat2` / `shots/watch` 即可，注意 `combat2/contact.png` 是拼图，要跳过。）
